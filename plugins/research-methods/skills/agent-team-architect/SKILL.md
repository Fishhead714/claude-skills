# Agent Team Architect

判断"要不要建 agent / 团队怎么分"的决策框架，本身不产出 agent 文件，只产出判断。建议把团队现状
（有哪些 agent、各归哪个团队、历史事故案例）记在你自己仓库里的一份总账文档（例如 `docs/agent-team-plan.md`）——本文档只是可反复套用的检查清单，
现状只在总账里维护，**不要在这里重复**，避免两处漂移。

## 心智模型（先对齐，否则后面的判断题会跑偏）

- **Skill = 岗位说明书**：注入当前上下文的指令，没有独立窗口、没有权限边界，是"怎么做"。
- **Agent = 人**：独立上下文窗口+独立工具权限+可并行调度，是"谁来做"。
- **Team = 你画的边界线，不是运行时对象**：没有专属权限、没有专属通信通道，纯粹是"哪些 agent/skill 共享同一套判断标准"的组织约定。

## 一、要不要建新 agent / 归哪个团队——三问（判断题，不能脚本化，必须真的想）

1. **这活跟哪些已有活共享同一套背景知识和验收标准？** 答案就是团队边界，不是"同属一个项目"。
2. **这类产出有没有生产者却没有验收者？** 这才是新建 agent 的信号，不是"这个领域重要"。生产者和验收者都已存在，通常不需要再建。
3. **能不能钉出一个真实发生过的事故，作为这个 agent 存在的理由？** 钉不出来就先别建——先攒案例，不要先设计"应该检查什么"再倒推案例。

三问全部走完之前不要动手建。

## 二、拓扑怎么选

| 拓扑 | 什么时候用 |
|---|---|
| 委派 | 单点深挖，不需要别人配合 |
| 扇出（有屏障） | 阶段 N 真的需要阶段 N-1 的**全部**结果（去重/跨条目对比/零结果早退） |
| 流水线（无屏障） | 多阶段加工，条目互不依赖——**默认选这个** |
| 裁判庭（独立盲审） | 结论要真正交付出去，需要防锚定的对抗性验证——各裁判互不通气，各自投票 |
| 辩论（互相交锋） | 根因未知/多假设待验证/架构取舍类任务——独立调查后**互相直接消息交锋**，共享一份 append-only 日志（用 Edit 追加，别用 Write，防并发覆盖），限 2-3 轮，最后由不参与辩论的主持人收敛结论 |

没有"必须等齐"的理由，就用流水线，别用扇出。裁判庭防锚定，辩论逼近真相——结论有唯一对错用裁判庭，结论是权衡取舍才用辩论；辩论模式更贵，没有真正"根因未知"的场景时先记为可选项，不强推（辩论模式及其共享日志做法取自 creating-agent-teams 项目的 Discussion Mode，见 THIRD_PARTY_NOTICES.md）。

## 三、模型分级怎么选

不是每个 agent 都该 `model: inherit`。评审型/判断型 agent 继续 inherit，判断力优先于成本；但新建"检索/收集型"agent（只做机械查找，不做判断）时，按信号分级：

| 信号 | 模型 | 理由 |
|---|---|---|
| 检索/grep/找文件/列模式 | haiku | 机械动作，不需要推理 |
| 简单编辑/模板化/格式化 | haiku | 照模式填空 |
| 跨大量文件收集数据 | haiku | 要的是覆盖面不是深度 |
| 有明确 spec 的功能实现 | sonnet | 需要较强代码生成+推理 |
| 排障/根因分析 | sonnet | 要追踪链路、提假设 |
| 代码审查/写测试 | sonnet | 限定范围内的判断 |
| 架构设计/开放式问题 | opus | 权衡取舍多，判断力优先 |
| 协调 4+ 个 agent 当 lead | opus | 编排复杂度高 |

金字塔模式：haiku 负责广泛收集 → sonnet 负责精加工 → opus 只做协调判断，不要让贵模型去跑 grep（上表与金字塔模式译自 creating-agent-teams 项目的 Model Selection by Task Signal，见 THIRD_PARTY_NOTICES.md；分级未经作者实测，是方向性判断，不是精确数字）。

## 四、建 agent 前逐条核对的五条硬约束（全部来自真实事故）

1. 不用 `general-purpose` 当团队成员——它自带 Agent 工具，会自己递归再派单，token 失控。
2. `tools` 字段必须实证验证，不能只看声明——声明可用 ≠ 子 agent 环境里真的可达。
3. 生产者不能自审——裁判必须由主线程直接派单，不能让生产它的 agent 自调。
4. 并发扇出宽度 ≤ 4-5——每个子 agent 会话各起一份 MCP 进程，重量级 MCP 服务器每会话可常驻 1GB 以上内存，没有内存限流时真实 OOM 过。
5. 评审型 agent 一律不给 `Edit`——权限即职责，"只报告不修改"要靠工具权限硬约束，不能靠自觉。

## 五、写法约定

```
---
name: <kebab-case>
description: <何时该叫它 + 何时不该叫它，两者都要写，这是自动触发不误伤的关键>
tools: <最小集合>
model: inherit    # 除非有明确理由
---

<第一人称角色声明，含"你没写这个东西，没有维护它好看的动机">

## Why this agent exists

<一个真实历史事故 + 根因拆解，每条检查项对应一个失败模式>
```

## 六、日常管理节奏

- 新增 skill 时先套第一问判断它属于哪个既有团队边界，不要默认需要新团队。
- 会话内新建**或编辑**的 agent 当场可能派不到最新版——注册表在会话启动时定死，建完/改完通常要等一次 `/reload-plugins`（或开新会话）才能验证派单层真的读到最新内容，规划时把这一步算进流程，不要标记"建完=验完"。作者实测过一次编辑场景：某个 agent 定义加了一条新检查项、提交推送、插件缓存也确认已刷新到含新内容的版本，但同一会话里派单验证时，子 agent 收到的仍是旧快照——脚本本身跑通不代表派单层已经生效，这两件事要分开验证。
- 落地记录如实写"待验证"，不要标完成了事——数据/环境不在线时只能做静态验证，要留痕，之后数据可用时回来补（真实案例：一条报告管线的端到端复核就是拖到数据副本上线才补上的）。
- 团队扩张后定期让横向裁判（如 secrets-auditor）扫一遍新增内容——护栏本身也会有盲区（比如提交前检查漏扫某个目录），不要等出事才发现。
- 建完/改完团队结构后，把变化回写进你的团队总账文档，保持它是唯一真相源，不要让判断散落在对话记忆里。
- 后台派单（`run_in_background:true`）且**需要写文件**的 agent，要先确认 `~/.claude/settings.json` 的 `permissions.allow` 已预批准 `Write`/`Edit`——后台 agent 无法弹权限确认框，未预批准的工具直接静默拒绝，`mode` 参数不能绕过这条。评审型后台 agent 不给 Edit，撞不上这个坑；建"会写文件的后台 agent"前要先查这条（取自 creating-agent-teams 项目的 Common Mistakes，见 THIRD_PARTY_NOTICES.md）。

## 七、Claude Code 原生还有一条"Agent Teams"通道，跟本文档不是一回事

Claude Code 官方存在一个实验性的多进程"Agent Teams"特性（`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` 环境变量开启）——多个独立 `claude` 进程作为"队友"实时协作、可跨轮次互相追问，跟本文档讲的"派单给一次性子 agent"是不同的运行时机制。本文档的三问/拓扑/五条约束对该特性同样适用（"要不要建、建给谁看"的判断不变），但它的具体使用方式没有在这里展开——本文作者尚未验证过它的实际可用性和效果。用之前先验证，别假设它是免费的升级。
